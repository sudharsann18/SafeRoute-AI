# SafeRoute – AI-Powered Safe Route Recommendation System

A route recommendation system that does not consider only the shortest distance. SafeRoute analyzes multiple safety factors (crime risk, lighting, traffic, time of day, road risk, distance), predicts route risk with a **Random Forest Classifier**, and uses a **manual Dijkstra's algorithm** with a combined distance + safety cost to recommend a safer route.

> **Important limitation:** This prototype uses **synthetic/demo safety data** for crime, lighting, traffic, and road-risk factors. It does **not** use real police databases or live traffic APIs. A production system would require verified real-world datasets and APIs.

---

## 1. Project Overview

SafeRoute helps a user find a safer path between two points. Instead of only minimizing distance, it computes a safety score for each route segment, predicts risk using machine learning, and runs Dijkstra's algorithm on a graph of segments where edge cost balances distance and safety. The result is a route that may be slightly longer but is safer.

## 2. Problem Statement

Standard navigation apps optimize for the shortest or fastest path. However, the shortest path is not always the safest — it may pass through poorly lit areas, high-crime zones, or dangerous roads. SafeRoute addresses this by making safety a first-class factor in route selection.

## 3. Solution

SafeRoute combines:

- **OpenStreetMap** data via **Nominatim** (geocoding) and **OSRM** (routing)
- A **Random Forest Classifier** trained on a reproducible synthetic dataset that predicts whether a segment is high or low risk
- A **deterministic safety scoring formula** (no randomness in the final score)
- A **manual Dijkstra implementation** that minimizes a combined distance + safety cost
- A **React + Leaflet** dashboard that visualizes routes, safety scores, alerts, and recommendations

## 4. Features

- Interactive dark-themed map with current location and destination markers
- Destination search with geocoding (Nominatim)
- Multiple route alternatives from OSRM
- Per-route safety score (0–100), risk level (LOW / MEDIUM / HIGH)
- ML risk prediction with confidence
- Route comparison cards with distance, duration, safety score, risk level
- Safety analysis panel with all six safety factors visualized
- Contextual alerts (crime, lighting, traffic, time, road risk) shown only when a factor is responsible
- Dijkstra-optimized safer route highlighted in blue
- Color-coded routes: green (low), amber (medium), red (high), blue (recommended)
- Clickable routes that update the analysis panel
- Browser geolocation with fallback
- Error handling for location denied, destination not found, backend unavailable, empty routes

## 5. Architecture

```
User enters destination
        |
        v
React frontend (Leaflet map + dashboard)
        |
        v  (HTTP POST)
Flask backend
        |
        +--> Nominatim (geocoding)
        +--> OSRM (route geometry with alternatives)
        |
        v
For each candidate route:
   1. Split geometry into segments
   2. Compute deterministic safety features per segment
   3. Random Forest predicts segment risk
   4. Safety score calculated (weighted formula)
   5. Graph built from segments (nodes = points, edges = segments)
   6. Dijkstra minimizes combined distance + safety cost
        |
        v
JSON response (routes, safety scores, ML predictions, alerts)
        |
        v
React renders routes on map + safety dashboard
```

## 7. ML Workflow

1. **Dataset creation** (`models/risk_model.py`): A reproducible synthetic dataset of 4000 rows is generated with NumPy. Features: `crime_risk`, `lighting_score`, `traffic_level`, `time_risk`, `road_risk`, `distance`. The target `risk` (0 = low, 1 = high) is generated by a deterministic weighted rule (not random) so the model learns a meaningful mapping.

2. **Training**: A `RandomForestClassifier` with 120 estimators is trained on an 80/20 train/test split. The model is trained **once** when the backend starts and persisted to disk with joblib. It is **not** retrained on every request.

3. **Prediction**: The `predict()` function takes a segment's safety features and returns a binary prediction (0/1), a label (LOW/HIGH), and the prediction probability (confidence).

4. **Accuracy**: The model typically achieves ~94–99% test accuracy on the synthetic dataset.

## 8. Safety Scoring Methodology

The safety score is a 0–100 value where higher = safer. It is computed deterministically (no randomness):

```
penalty = 0.30 * crime_risk
        + 0.15 * traffic_level
        + 0.15 * time_risk
        + 0.25 * road_risk
        + 0.05 * distance_normalized

lighting_bonus = 0.20 * lighting_score

safety_score = clamp(100 - penalty + lighting_bonus, 0, 100)
```

Where `distance_normalized = (distance_m / 2000) * 100`, clamped to 100.

Risk level mapping:
- `safety_score >= 70` → LOW risk
- `safety_score >= 45` → MEDIUM risk
- `safety_score < 45` → HIGH risk

Weights are configurable in `services/safety_scoring.py`.

## 9. Dijkstra Algorithm Explanation

The Dijkstra implementation is in `algorithms/dijkstra.py`. It is written manually — no library "dijkstra" function is called.

**Why a graph?** A route is a sequence of coordinates. We treat each coordinate as a node and the stretch between consecutive coordinates as an edge. Each edge stores distance, safety score, and a combined cost.

**Edge cost calculation:**
```
normalized_distance = distance / max_segment_distance   (0..1)
normalized_risk     = (100 - safety_score) / 100         (0..1)

edge_cost = distance_weight * normalized_distance
          + safety_weight * normalized_risk
```

Default weights: `distance_weight = 0.4`, `safety_weight = 0.6`. Increasing `safety_weight` makes Dijkstra prefer safer edges over shorter ones.

**How Dijkstra selects the minimum-cost node:** A min-heap (priority queue) is used. The node with the smallest known cumulative cost is always processed next. When a neighbor is reached with a lower cost than previously known, its distance and predecessor are updated.

**Path reconstruction:** After the target is reached, the path is reconstructed by following `prev` pointers backwards from target to source, then reversed.

This means the selected route can be slightly longer but safer than the shortest-distance route.

## 10. API Endpoints

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/` | Service info + model metadata |
| GET | `/api/model` | Model info (algorithm, accuracy, features) |
| POST | `/api/geocode` | Geocode a destination via Nominatim |
| POST | `/api/routes` | Full route recommendation pipeline |
| POST | `/api/predict-risk` | ML risk prediction for given features |

## 11. Frontend/Backend Workflow

1. The user clicks "Use my location" — the browser's geolocation API provides the origin.
2. The user types a destination and clicks "Find Safe Routes".
3. The frontend sends `POST /api/routes` with origin and destination to the Flask backend.
4. Flask geocodes the destination (Nominatim), fetches routes (OSRM with alternatives), analyzes each route's safety, runs the ML model and Dijkstra, and returns JSON.
5. The frontend renders all routes on the Leaflet map, color-coded by risk, with the recommended route in blue.
6. Route cards show distance, duration, safety score, risk level, and ML prediction.
7. Clicking a route updates the safety analysis panel and alerts.

## 15. Limitations

- **Synthetic data**: Crime, lighting, traffic, and road-risk factors are generated by deterministic synthetic formulas, not real-world data sources. This is clearly a prototype limitation.
- **External APIs**: Nominatim and OSRM are public free-tier services with rate limits. Heavy usage may be throttled.
- **No real-time data**: The system does not pull live traffic or crime feeds.
- **Routing scope**: OSRM provides driving routes; walking/cycling profiles are not used in this prototype.
- **Safety model**: The ML model is trained on synthetic data with a known rule; real-world performance would depend on genuine labeled data.

## 16. Future Improvements
